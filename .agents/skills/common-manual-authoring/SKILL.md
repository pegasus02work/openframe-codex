# OpenFrame 매뉴얼 작성

## 적용과 경계

- [팀 작업 가이드](https://tmaxsoft.atlassian.net/wiki/spaces/MW33/pages/2377056721/OpenFrame+Wiki+openframe-manual-wiki)를 절차 근거로 사용한다. 실행 시 현재 대상 Jira·위키 상태를 확인하며 과거 사례를 현재 검증 결과로 취급하지 않는다.
- 이 스킬은 반영 경로와 작성 기준을 담당한다. 접속·제품/버전/OS 선택·인증·권한·원문 확보·편집·충돌 방지·저장 검증은 [common-manual-wiki](../common-manual-wiki/SKILL.md)의 절차를 단일 기준으로 적용한다.
- 스킬 추가나 초안 작성 요청을 Jira·위키 쓰기 권한으로 해석하지 않는다. 쓰기가 요청 범위에 포함된 경우 승인된 대상과 변경을 수행하며, 이미 명시적으로 승인된 작업은 중복 확인하지 않는다. 기능 노트만 요청받았다면 본문 수정이나 Jira 상태 전환까지 확대하지 않는다.
- Jira 조회는 [common-tmaxsoft-jira-read](../common-tmaxsoft-jira-read/SKILL.md)를 따른다. 이 읽기 전용 스킬로 필드 변경·댓글·전환을 하지 않는다. Jira 쓰기는 별도로 허용된 도구와 명시적 권한이 있을 때만 수행하고 그렇지 않으면 사용자 처리 항목을 제시한다.

## 반영 경로

| 변경 성격 | 반영 경로 |
| --- | --- |
| 완전 신규 기능 | 기능 노트 작성 필수 |
| 기존 문구·예제·속성·설정값 수정 | 본문 직접 수정 가능. 사용자 영향이 있으면 기능 노트 병기 권장 |
| 오탈자·형식 등 경미한 수정 | 본문 직접 수정 |

기능 노트를 작성하고 작성자가 본문도 수정하는 패턴을 권장한다. 기능 노트만 작성하여 TD팀이 본문에 반영하는 패턴도 가능하다. 권장 사항을 필수로 확대하지 말고 요청 범위를 따른다. 경로가 불명확하면 사실·영향·선택안을 제시하고 필요한 결정을 확인한다.

## 기능 노트 작성

1. Jira 이슈 유형, '기능 노트 작성(매뉴얼 반영)' 필드, 기존 하위 작업, 노트 페이지와 태그부터 확인하여 중복 생성을 피한다.
2. 필드 체크 대상은 개별 스토리·작업·버그다. 에픽·하위 작업에는 체크하지 않는다. 잘못 체크한 뒤 회수할 수 있다고 가정하지 않는다.
3. 승인된 Jira 쓰기가 가능한 경우에만 필드의 '필요'를 체크한다. 자동 생성된 '기능 노트 작성' 하위 작업의 설명에서 실제 편집 링크를 연다. 편집 URL이나 템플릿 번호를 추측하지 않는다.
4. `docs/openframe/feature-notes/<티켓키>`의 평면 구조를 탐색 단서로 삼되 실제 링크와 페이지 경로로 대상을 확인한다. 위키가 제공하는 템플릿을 우선 사용한다. 초안용 보조 양식은 [assets/feature-note-skeleton.md](assets/feature-note-skeleton.md)를 사용한다.
5. 제목은 `<기능명> (<티켓키>)`, 문체는 '~합니다' 체를 기본으로 한다. 제품·버전, 기능 개요, 개발 유형, 목적·사용 시나리오, 사용 방법·주요 동작, 주의사항·예외, 관련 자료를 담되 해당 없는 항목은 생략하거나 변형한다. '매뉴얼 수정 지점'에는 실제 문서/절과 수정 전·후를 명시하고, 대상 페이지가 없으면 그 사실을 적는다.
6. 작성 완료 시 승인된 범위에서 `done` 태그를 추가한다. 제품 태그 `of_<제품>`와 키워드 태그는 선택 사항이며 기존 태그를 보존한다. `applied`는 TD팀의 본문 반영 완료 의미이므로 작성자가 임의 부여하지 않는다.
7. 작성자의 기본 책임은 `done`과 Jira 하위 작업 완료까지다. 본문 반영은 요청 범위와 선택한 패턴에 따른다. Jira 전환은 현재 가능한 전환과 목적 상태를 확인하고 자기 상태로 돌아오는 전환을 피한다. 프로젝트 이름만으로 상태 경로나 전환 ID를 고정하지 않는다.

### 기존 상태에 따른 재개

| 현재 확인한 상태 | 처리 |
| --- | --- |
| 필드 미체크·하위 작업 없음 | 대상 판단부터 시작 |
| 하위 작업 있음·노트 미작성 또는 미완료 | 기존 링크와 내용을 확인하고 남은 단계부터 진행 |
| 노트에 `done` | 중복 작성하지 않는다. 하위 작업 상태를 별도로 확인하고 보완 요청이 있으면 기존 노트를 수정 |
| 노트에 `done`·`applied` | 완료 기록을 확인한다. 새 요청이 없으면 다시 작성하지 않음 |

태그만으로 Jira 완료나 실제 본문 내용을 추정하지 않는다. 다른 담당자가 진행 중인 작업은 요청된 변경 범위와 담당 관계를 확인하고 기존 내용을 덮어쓰지 않는다.

### 내용의 근거와 예시

- Jira 설명은 구현 중 낡을 수 있다. 최종 구현과 승인된 실행 결과를 기준으로 사용자 동작을 재확인하고, 실제로 확인하지 않은 내용을 확정하지 않는다.
- 사용 방법에는 필요한 사전 설정, 입력·옵션, 설정 예시, 실행 방법과 결과 확인 방법을 포함한다. 실제 출력이라고 제시하는 예시는 확인한 결과와 일치시킨다. 설명용 예시·예상 출력은 실측과 구분해 표시한다.
- 문장 다듬기보다 사용자가 기능을 쓰는 데 필요한 정보의 완전성을 우선한다. 비공개 구현은 루트 지침의 공개 정보 범위에 따라 제외한다.

## 본문 작성과 수정

- 해당 버전·OS의 동작을 매뉴얼·승인된 현재 소스 또는 실행 근거로 먼저 확인한다. 문서 작업 요청을 제품 코드 수정이나 런타임 실행 권한으로 확대하지 않는다. 근거가 부족한 사양은 초안에 미확인으로 표시하고 확정하지 않는다.
- 같은 문서가 `7_1`, `7_3`, `7_4` 등에 존재할 수 있다. 관련 버전의 실제 페이지와 적용 여부를 확인하되 다른 버전의 내용을 그대로 복제하거나 요청 범위 밖 페이지를 자동 수정하지 않는다.
- 본문은 AsciiDoc과 '~한다' 체를 사용하고 주변 문단의 용어·표기·구조를 따른다. `(((용어)))` 색인 마커와 `:imagesdir:`, `:sectnums:` 등 기존 헤더 속성을 보존한다.
- 이미지 경로는 기존 `:imagesdir:` 기준과 `image::` 문법을 유지한다. 표의 열 속성과 `|===` 구분자, 절차 목록의 `[arabic]`·`.` 형식 등 주변 AsciiDoc 구조를 보존한다. 다른 형식으로 일괄 변환하지 않는다.

## 완료 보고

문서 URL과 제품·버전·OS, AS-IS → TO-BE 핵심 차이, 근거와 저장·렌더링 확인 결과를 보고한다. 기능 노트 작성, `done`, Jira 하위 작업 완료, 본문 반영 여부를 각각 구분하고 수행하지 못한 항목을 명시한다. TD팀 반영 완료나 타 버전 검증을 추정하지 않는다.
