# 완료 이슈 정리

사용자가 정리를 요청한 이슈에 한해 실행한다. 스킬 작성·수정 요청은 실제 이슈 삭제 요청이 아니다.

## 적용 범위와 기존 지침

- [루트 AGENTS.md](../../../AGENTS.md)의 환경 선택·접속·인증·Git·위험 명령 기준을 따른다. 로컬 지침 저장소와 실제 제품 저장소를 구분하고, 제품 저장소 조작은 선택한 프로필의 환경에서 수행한다.
- [common-issue-artifacts](../common-issue-artifacts/SKILL.md)의 저장 위치와 기존 문서를 읽어 정확한 이슈 범위를 확인한다. 정리를 위해 분석 문서를 새로 만들거나 후속 분석의 디렉터리 선택 절차를 반복하지 않는다.
- 기본 범위는 해당 이슈를 위해 Codex가 생성한 산출물 디렉터리, 생성한 로컬·원격 이슈 브랜치, Jira에서 다운로드하여 분석 위치로 옮긴 재현 케이스·로그·core 등의 파일과 사본이다. 사용자가 일부만 요청하면 그 범위만 정리한다.
- 제품 소스·등록된 테스트, 설치 바이너리, DB·데이터셋, 운영 로그, Jira 원본 첨부·이슈, Codex 채팅 자체는 삭제하지 않는다. 별도 요청 없는 커밋·코드 push·병합·서비스 변경을 수행하지 않는다. 원격 이슈 브랜치 삭제는 요청된 정리 범위에 포함된다.

## 현재 상태와 컨텍스트 처리

- 정리 요청을 이유로 별도 컨텍스트 요약·인계 문서 작성이나 수동 압축 절차를 선행하지 않는다. 현재 저장소와 실제 파일 상태를 우선 확인하여 정리 여부를 판단한다.
- 파생 전 브랜치·삭제 대상의 생성 및 전송 근거·사용자 승인 범위를 확인하는 데 필요한 기존 기록만 선택적으로 읽는다. 과거의 완료·푸시·병합 기록으로 현재 상태 검증을 대체하지 않는다.
- 클라이언트의 자동 컨텍스트 압축은 이 지침의 제어 대상이 아니다. 자동 압축이 발생해도 현재 상태를 다시 확인하고, 보존된 승인 범위와 확인 근거에 따라 작업을 이어간다. 승인 범위나 대상이 불명확하면 추측하지 않고 필요한 부분만 사용자에게 확인한다.

## 정리 대상 확정

1. 사용자 요청과 현재 세션·기존 산출물에서 이슈 ID, 환경, 저장소, 생성한 이슈 브랜치, **실제로 파생한 기준 브랜치**와 각 원격/upstream을 확인한다. 브랜치 이름의 접두사, 원격 HEAD, `@{-1}` 또는 merge-base 하나만으로 파생 전 브랜치를 단정하지 않는다. 생성 당시 기록·reflog 등으로 확인할 수 없으면 사용자에게 묻는다.
2. 로컬 `investigations/<Jira-ID>/` 및 숫자 접미사 디렉터리, 원격 분석 작업 디렉터리, 첨부의 다운로드·전송·압축 해제 위치와 사본을 기존 기록에서 찾는다. 접미사가 붙은 별도 문제는 함께 완료·정리 요청된 범위인지 확인한다. 이름이 비슷하다는 이유로 일괄 포함하지 않는다.
3. 삭제 목록을 실행 위치(로컬/서버/컨테이너), 절대 경로, 생성·전송 근거, 종류와 함께 작성한다. 공유 디렉터리는 해당 이슈의 파일만 열거하고, 다른 작업이 쓰는 자료·출처 불명 자료는 제외하여 사용자에게 확인한다. 파일 전체나 core 내용을 불필요하게 출력하지 않는다.
4. 각 저장소의 `git status --short`, staged/unstaged diff, untracked 파일 및 `git worktree list --porcelain`을 확인한다. 삭제할 산출물과 미커밋 제품 변경을 구분한다. 다른 worktree에서 사용 중인 브랜치는 강제로 삭제하거나 worktree를 제거하지 않는다.

## 삭제 전 필수 검증

검증은 저장소별로 수행한다. 이슈 브랜치가 여러 개면 모두 검사한다. 다음은 명령의 의미이며 실제 명령에는 확인한 ref와 현재 셸에 맞는 인용을 사용한다.

| 검사 | 통과 기준과 확인 방법 |
| --- | --- |
| 변경 커밋 여부 | 이슈 작업의 제품·테스트 변경이 커밋되어 있고 해당 미커밋/staged/untracked 변경이 남지 않음. 정리 대상인 보고서·분석 사본은 구분. 미커밋 변경이 있으면 파일과 손실 범위를 제시 |
| 원격 푸시 여부 | 확인한 원격에서 fetch가 성공한 뒤 이슈 로컬 tip이 원격 이슈 브랜치에 포함됨을 `git merge-base --is-ancestor <issue-tip> <remote-issue-ref>`로 검사. upstream 설정이나 과거 push 로그만으로 통과하지 않음 |
| 파생 전 브랜치 최신화 | 기존 변경을 보존하여 확인한 기준 브랜치로 `git switch`하고, 실제 upstream에 `git pull --ff-only` 성공. 실패·divergence·upstream 부재를 최신화 성공으로 간주하지 않음 |
| 병합 여부 | 최신화한 기준 브랜치에 이슈 tip이 포함되는지 `git merge-base --is-ancestor <issue-tip> <base-tip>`로 검사. fetch한 기준 브랜치 upstream에도 포함되어 있어야 함. 종료 코드 0만 통과, 1은 미포함, 그 밖은 검사 실패 |

- 본 작업 전 루트의 현재 브랜치 `pull --ff-only` 절차를 적용한다. 원격 이슈 브랜치가 이미 삭제되어 pull이 실패했으면 원인을 보고하고, 기준 브랜치 최신화와 원격 포함 검증을 계속할 수 있다. 그 실패 자체를 성공으로 표시하지 않는다.
- 원격 이슈 브랜치가 이미 없더라도 최신 원격 기준 브랜치에 이슈 tip이 포함되어 있으면 원격 보존·병합 근거로 사용할 수 있다. 확인된 원격 ref가 없거나 fetch가 실패하면 푸시 여부는 미확인이다.
- 원격 이슈 브랜치가 로컬보다 앞서면 **원격 tip도** 최신 기준 브랜치와 그 upstream에 포함되는지 검사한다. 로컬 tip만 병합되었다는 이유로 다른 사람의 원격 커밋을 삭제하지 않는다.
- squash/rebase/cherry-pick으로 ancestry 검사가 실패한 경우 patch 비교·PR 기록 등으로 실제 반영 상태를 조사하여 설명한다. 커밋 메시지나 tree 일치만으로 모든 변경이 푸시·병합됐다고 자동 통과시키지 않고 아래 예외 확인으로 넘긴다.
- 이미 삭제된 브랜치, 브랜치를 만들지 않은 분석 전용 작업은 그 사실과 근거를 명시한다. 검사할 tip을 복구·확인할 수 없으면 검증 불가로 처리한다. 분석 전용은 사용자가 해당 범위를 확인한 경우 Git 검사 비해당으로 진행한다.
- 기준 브랜치 최신화는 병합 여부 확인을 위한 선행 작업이며, **이 단계가 끝나기 전에는 파일이나 브랜치를 삭제하지 않는다.** 전환이 미커밋 파일 때문에 막히면 강제 전환·stash·reset·clean으로 우회하지 않는다.

## 검증 실패·미확인 시 사용자 결정

- 미커밋·미푸시·미병합 또는 검사 실패/불가가 있으면 삭제를 멈춘다. 저장소·브랜치·tip, 실패한 조건, 남은 커밋/파일, 삭제할 경로와 복구 가능 여부를 구체적으로 제시하여 **이 상태로 정리를 계속할지** 묻고 응답을 기다린다. 무응답은 승인이 아니다.
- 사용자가 예외 진행을 승인하면 승인한 브랜치·파일과 손실 범위만 처리한다. 예외가 로컬 브랜치 강제 삭제를 필요로 하면 그 필요와 미병합 커밋 손실을 질문에 포함한다. 미커밋 제품 파일 폐기는 별도 명시 대상이며 포괄적인 정리 동의로 `reset --hard`나 `clean`을 실행하지 않는다.
- 모든 조건이 통과하고 삭제 범위가 요청에서 확인되면 대상 목록과 검증 결과를 알린 뒤 정리한다. 동일 범위에 대한 확인은 반복하지 않는다. 새 대상이나 변경된 tip은 다시 검증하고 필요한 범위만 확인한다.

## 실행과 확인

1. 삭제 직전에 저장소·현재 브랜치·작업 트리·이슈 tip·원격 tip·경로를 다시 확인한다. 검사 후 변경이 있으면 재검증한다. 최종 작업 위치는 파생 전 기준 브랜치로 유지한다.
2. 확인한 원격 이슈 브랜치를 삭제한다. 원격 저장소와 `refs/heads/<issue-branch>`를 확인하고, 검사한 tip에 대한 `--force-with-lease=<ref>:<verified-tip>` 조건을 붙인 삭제 push로 다른 사람이 갱신한 브랜치를 지우지 않도록 한다. lease 불일치는 강제 재시도하지 않고 재검증한다. 원격이 이미 없으면 생략한다. 기준·공유 브랜치는 삭제하지 않는다.
3. 로컬 이슈 브랜치는 `git branch -d -- <issue-branch>`로 삭제한다. 실패하면 원인을 확인하며 자동으로 `-D`로 바꾸지 않는다. 앞서 승인받은 예외에 정확히 해당할 때만 해당 브랜치의 강제 삭제를 수행한다.
4. 브랜치 처리 성공 후 목록에 있는 분석 파일과 산출물 디렉터리를 삭제한다. 각 경로의 정규화된 절대 경로와 실제 대상을 확인하고 허용된 이슈 작업 경로 안인지 경로 요소 기준으로 검사한다. 루트·홈·저장소 전체·설치 루트·공유 상위 디렉터리는 재귀 삭제하지 않는다. 심볼릭 링크·junction·reparse point를 따라 경계 밖 파일을 삭제하지 않는다. 디렉터리 내부에 혼재한 자료도 확인한다.
5. Windows는 한 PowerShell 안에서 `-LiteralPath`를 사용해 처리하고 다른 셸에 삭제를 위임하지 않는다. POSIX도 확인한 개별 절대 경로를 인용하여 처리한다. glob, 이슈 ID의 부분 문자열, 저장소 전체 `git clean`으로 삭제 대상을 확장하지 않는다. Git 추적 산출물이면 삭제가 작업 트리에 남는다는 점을 먼저 알리고 자동 커밋·stage하지 않는다.
6. 삭제 후 파일 부재, 로컬 ref 부재, 원격 `ls-remote --heads`의 정상 조회와 해당 ref 부재, 기준 브랜치·upstream 동기화 및 최종 `git status`를 확인한다. 실패하면 그 단계에서 멈추고 남은 자료를 보존한다. 일부 성공은 부분 완료로 보고하며 삭제한 파일을 다시 만들지 않는다.

최종 답변에 삭제·생략·보존·실패 대상을 실행 위치별로 요약하고, 커밋·푸시·병합 검사 근거와 예외 승인, 복귀한 브랜치·최신화 결과, 남은 작업을 적는다. 정리 결과는 대화에 남기며 삭제한 산출물 디렉터리에 새 보고서를 만들지 않는다.
