# Jira 이슈 산출물 관리

분석·구현 절차를 담당하는 스킬과 함께 사용하여 작업 근거와 결정, 실제 결과를 이슈별로 이어서 기록한다.

## 기존 지침과의 연결

- [루트 AGENTS.md](../../../AGENTS.md)의 환경 선택·제품별 지침 라우팅·공개 정보와 내부 구현의 기록 범위·단계별 방향 확인·Git·보고 기준을 따른다. 이 스킬은 산출물의 저장 위치와 기록 시점·내용만 정한다.
- 이슈 내용은 [common-tmaxsoft-jira-read](../common-tmaxsoft-jira-read/SKILL.md), 서버 측 원인 조사는 사용 가능한 `openframe-issue-investigate`를 적용한다. 조사 보고서 양식을 사용하는 경우 분석 내용은 아래 분석 파일에 통합하고 별도 중복 보고서를 만들지 않는다.
- 구현·테스트는 루트의 「Jira 이슈 수정에서 테스트까지」를 따른다. 단위 테스트는 [common-unit-test-write](../common-unit-test-write/SKILL.md), 설정·빌드·JOB 등은 루트 라우팅의 해당 스킬을 적용한다. 이 스킬의 문서 작성은 제품 코드 수정·실행·실제 커밋 권한을 추가하지 않는다.

## 저장 위치와 이어서 작업하기

- 이 지침 저장소 루트에 `investigations/<Jira-ID>/`를 만들고 해당 이슈의 보고서·증거·재현용 보조 산출물을 저장한다. 원격 제품 소스 루트와 구분한다. 이슈 ID는 Jira 또는 사용자가 제공한 값으로 확인하며, 확인할 수 없으면 임의 ID로 디렉터리를 만들지 말고 확인한다.
- 이슈 디렉터리가 이미 있으면 기존 산출물을 먼저 읽고 아래 「다른 세션에서 같은 Jira 이슈를 처리할 때」에 따라 작업 디렉터리를 확정한 뒤 갱신한다. 이전 증거와 사용자 결정을 덮어쓰거나 추측으로 대체하지 않는다. 여러 환경·재실행의 증거는 식별 가능한 하위 경로나 이름으로 구분한다.
- 분석을 시작할 때 `analysis.md`와 `evidence/`를 준비한다. 나머지 문서는 아래 해당 단계에서 생성·갱신하며, 미진행 단계를 완료한 것처럼 채우지 않는다.
- 제품 코드와 등록할 테스트 소스는 실제 제품 저장소의 지정 경로에 둔다. 이슈 디렉터리에는 해당 경로·diff·검증 근거를 기록하며 제품 소스나 테스트를 중복 관리하지 않는다.

## 다른 세션에서 같은 Jira 이슈를 처리할 때

- 별개의 세션에서 같은 Jira 이슈의 추가 작업을 시작하면 `investigations/`의 해당 Jira ID 기본 디렉터리와 숫자 접미사가 붙은 디렉터리들을 확인하고, 각 `analysis.md`와 필요한 계획·구현 보고서를 읽어 기존 문제 범위와 사용자 결정을 파악한다. 세션이 달라졌다는 이유만으로 새 디렉터리를 만들지 않는다.
- **기존 처리 방식의 후속 처리:** 동일한 문제와 기존 처리 방식의 보완·추가 검증·후속 구현이면 해당 작업을 기록한 같은 디렉터리를 사용한다. 기존 작업이 숫자 접미사 디렉터리에 있다면 그 디렉터리에서 이어간다.
- **같은 이슈에서 보고된 다른 문제 처리:** 기존 작업과 다른 문제이면 `investigations/<Jira-ID>-2/`를 새로 만들어 독립적으로 기록한다. 이미 사용된 번호가 있으면 기존 디렉터리를 재사용·덮어쓰기하지 않고 확인한 최대 번호 다음의 `-3`, `-4` 순서로 제안한다. 숫자 접미사는 산출물 구분이며 Jira ID 자체를 바꾸지 않는다.
- 기존 자료로 분기를 판단할 수 있으면 **진행하려는 방식, 판단 근거와 정확한 대상 디렉터리를 사용자에게 먼저 알리고 응답을 기다린다.** 판단할 수 없으면 처음부터 「기존 처리의 후속 작업」과 「같은 이슈의 다른 문제」 중 어느 쪽인지 묻고 답변에 따라 경로를 정한다. 사용자가 현재 세션에서 방식과 경로를 명시적으로 확정했다면 같은 확인을 반복하지 않는다.
- 사용자 응답으로 방식이 확정되기 전에는 해당 산출물 디렉터리의 신규 생성이나 기존 산출물 갱신을 진행하지 않는다. 기다리는 동안 기존 자료의 읽기 전용 확인은 계속할 수 있다. 응답이 없다는 이유로 임의 선택하지 않는다. 새 번호 디렉터리 생성 직전에 경로가 여전히 사용되지 않았는지 확인하고, 다른 작업이 선점했으면 갱신한 경로를 다시 알리고 확인한다.
- 확정 후 선택한 디렉터리의 `analysis.md`에 실제 Jira ID, 이번 작업의 문제 범위, 선택한 처리 방식과 사용자 결정 근거, 관련 기존 디렉터리 링크를 기록한다. 이후 보고서와 `evidence/`는 모두 선택한 디렉터리에 두며, 관련 자료는 링크로 연결해 중복 복제하지 않는다.

## 파일별 기록 기준

아래 경로는 모두 위 절차로 확정한 작업 디렉터리(`investigations/<Jira-ID>/` 또는 `investigations/<Jira-ID>-<번호>/`) 기준이다.

| 경로 | 생성·갱신 시점 | 기록할 내용 |
| --- | --- | --- |
| `analysis.md` | 분석 시작 및 조사 결과 변경 시 | Jira ID·출처, 요구사항·재현 조건·기대 동작, 확인한 환경·소스 기준, 제품 라우팅, AS-IS와 원인 분석, 사실·추론·미확인 구분, 증거 링크, 남은 질문과 다음 확인 항목 |
| `evidence/` | 근거를 확보할 때마다 | 분석·구현·검증을 뒷받침하는 명령 출력, 로그, 조회 결과, 필요한 diff·테스트·커버리지 자료 등 |
| `fix-proposal.md` | 수정안을 제시할 때 | 가능한 선택안별 AS-IS → TO-BE, 변경 지점, 기대 효과·영향 범위·위험·검증 방법, 권고안과 미확인 사항. 예상 효과와 실측 결과를 구분 |
| `implementation-plan.md` | 사용자가 선택안을 결정한 뒤, 구현 전 | 선택안·선택 이유·기각한 대안과 이유·결정 상태·사용자 결정 근거·변경 이력, 요구사항별 파일·함수 단위 작업 순서와 변경 범위, 초기 테스트 계획·검증 명령·완료 조건. 이후 방향·검증 범위 변경과 확인 상태를 갱신 |
| `implementation-report.md` | 허가된 구현을 진행할 때부터 완료까지 | 수정 전·후 각각의 기준 소스와 파일·함수·줄 번호를 연결한 AS-IS → TO-BE, 사용자 지침·계획과 실제 diff의 대응 및 차이, 구현 후 방향 확인 상태, 빌드·테스트·gcov 결과와 근거 링크, 실패 원인·미검증·남은 작업 |
| `commit-message.md` | 구현 완료 후 | 실제 diff에 맞는 Git 커밋 메시지 초안. 저장소의 기존 형식에 맞춰 Jira ID, 변경 목적·내용 및 검증 결과를 반영하고 실패·미검증을 성공으로 표현하지 않음 |

## 보고서 단위와 조건부 분리

### AS-IS와 TO-BE의 시각적 구분

- 변경을 비교하는 문서의 각 항목은 루트 `AGENTS.md`의 보고 기준에 따라 작성한다. 짧은 비교는 `AS-IS`·`TO-BE` 열이 있는 표로, 긴 비교는 아래처럼 소제목 또는 독립된 굵은 레이블과 빈 줄로 구분한다.
- `implementation-plan.md`의 선택한 구현과 `implementation-report.md`의 제품·검증 코드 변경 설명에도 적용한다. 파일명·상세 절차는 해당 설명 아래에 배치한다.
- 작성 후 렌더링 기준으로 두 상태가 별도 블록으로 보이는지 확인한다. 원문에서 행만 나눈 `AS-IS: ...`와 `TO-BE: ...`는 한 문단으로 합쳐지므로 사용하지 않는다.

```markdown
### AS-IS

현재 상태와 문제를 설명한다.

### TO-BE

변경 후 상태와 유지할 동작을 설명한다.
```

### 구현 보고의 코드 위치 표기

- `implementation-report.md`에서 실제 코드를 근거로 설명하는 AS-IS와 TO-BE에는 각각 해당 설명을 뒷받침하는 파일 경로·함수명·1부터 시작하는 줄 번호 또는 줄 범위를 함께 적는다. 문단형은 각 상태의 본문에, 표형은 해당 상태의 셀이나 명확히 연결된 근거 열에 표시한다. 문서 앞에 변경 함수의 전체 범위만 한 번 적는 것으로 대신하지 않는다.
- AS-IS는 수정 전 커밋 등 기준 소스의 줄 번호를, TO-BE는 실제 수정 후 소스의 줄 번호를 사용하고 두 기준을 명시한다. 미커밋 소스는 기준 커밋과 함께 보관한 diff·소스 스냅샷 등으로 식별한다. 작업 순서나 추가·삭제 줄 개수를 코드 위치 대신 사용하지 않는다.
- 제품 코드뿐 아니라 검증 코드 변경 설명에도 적용한다. 파일·코드가 새로 생겼거나 삭제되어 해당 상태에 줄 번호가 없으면 그 사실과 비교한 트리·diff 근거를 적고, 존재하지 않는 줄 번호를 만들지 않는다.
- lex/yacc(flex/bison)는 원본 `.l`·`.y`의 줄 번호를 기준으로 설명한다. 생성 C·헤더의 줄 번호로 대신하거나 검토용 diff에 생성물을 추가하지 않는다. 줄 번호는 실제 해당 소스·diff에서 확인하며, 확인할 수 없으면 미확인과 사유를 명시한다.

### 문서 분리 기준

- 기본은 위 단계별 문서를 유지한다. 문서 수를 늘리는 것보다 각 문서의 목적과 갱신 책임을 명확히 하고, 같은 분석·결정·검증 결과를 여러 문서에 복사하지 않는다. 요약과 원본 문서의 상대 링크로 연결한다.
- `implementation-plan.md`의 결정 기록에는 선택안, 선택 이유, 기각한 대안과 이유, 결정 상태, 사용자의 결정 근거를 명시한다. 결정이 변경되면 이전 결정과 이유를 보존하고 변경 내용·근거와 새 결정의 관계를 기록한다. 문서 작성이나 상태 표기만으로 사용자 확인을 대신하지 않는다.
- 일반적인 결함 수정의 결정은 위 계획 문서의 절로 기록한다. 구조·인터페이스·의존성·비기능 특성 등 장기적으로 영향을 주는 중요한 설계 결정만 별도 ADR(Architecture Decision Record)로 분리한다. 해당 저장소의 기존 ADR 경로·번호 규칙을 우선하며, 별도 규칙이 없으면 이슈 디렉터리의 `decisions/` 아래 결정별 Markdown 파일로 기록한다. 배경·결정·상태·결과를 포함하고, 대체된 결정은 삭제하지 않고 후속 결정으로 연결한다. 계획 문서에서는 ADR을 참조한다.
- 빌드·테스트·gcov·JOB 검증은 기본적으로 `implementation-report.md`의 검증 절에 기록한다. 여러 환경·회차의 검증이 구현 보고와 독립적으로 진행·갱신되어 별도 관리가 필요할 때만 이슈 디렉터리에 `validation-report.md`를 만든다. 이때 검증 상세의 기준 문서는 `validation-report.md`로 삼고 구현 보고에는 요약·미검증 항목과 링크를 남긴다.
- `validation-report.md`에는 대상 소스·빌드 기준, 환경·입력·명령, 요구사항별 검증 항목과 기대값, 실행 결과·증거 링크, 실패 원인·남은 공백을 연결한다. 테스트 함수별 결과·gcov·JOB 실행 기록의 필수 항목은 담당 지침과 스킬을 그대로 따르며 중복 정의하지 않는다.
- 실제 서비스 장애의 영향·대응 과정·재발 방지 조치를 별도로 회고할 필요가 있을 때만 이슈 디렉터리에 `postmortem.md`를 추가한다. 영향, 타임라인, 대응·복구, 원인과 기여 요인, 교훈, 후속 조치와 담당·완료 기준을 기록한다. 확인되지 않은 원인·담당·기한은 미확인으로 표시하며 개인 비난 대신 시스템과 절차의 개선에 초점을 둔다. 원인 분석·구현·검증 상세는 기존 문서로 연결한다. 일반 결함 분석만으로 회고 문서를 필수 생성하지 않는다.

## 증거와 문서 간 연결

- 증거를 인용하는 문서에 `evidence/` 아래 자료의 상대 링크와 수집 명령·작업 디렉터리·비민감 환경 정보·수집 시점을 함께 적어 재현 가능하게 한다. 정적 소스 근거는 파일·위치와 소스 기준을, 런타임 근거는 실제 조회 필드·값과 실행 결과를 연결한다.
- 원격에서 얻은 필요한 증거도 이슈의 로컬 `evidence/`에 저장한다. 저장하지 못한 자료는 원격 위치와 사유를 명시하고 로컬 수집 완료로 표시하지 않는다. 비밀값은 저장 전에 가리며 불필요한 소스 전체·로그 전체를 복제하지 않는다. Jira 첨부 다운로드는 Jira 읽기 스킬의 권한 조건을 따른다.
- 분석 결론은 `analysis.md`, 대안 비교는 `fix-proposal.md`, 결정한 계획은 `implementation-plan.md`, 실제 결과는 `implementation-report.md`를 기준으로 삼고 다른 문서에서는 상대 링크로 연결한다. 테스트 함수별 결과·gcov와 JOB 실행 기록은 담당 지침의 내용을 보존하되 해당 단계 문서에서 근거를 연결한다.
- 구현이 진행 중이거나 검증이 막혔으면 `implementation-report.md`에 현재 상태와 남은 검증을 명시한다. `commit-message.md` 작성 자체로 staging·커밋·push를 실행하지 않는다.
- 최종 답변에는 생성·갱신한 문서 링크와 작업·검증 상태를 제시한다. 산출물이나 문서에 기록된 선택안을 사용자 승인으로 간주하지 않고 실제 대화의 결정과 연결한다.
